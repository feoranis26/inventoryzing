# inventoryzing Architecture Amendment 006

**Status:** Accepted architectural amendment  
**Scope:** Trusted module frontend capabilities and correction to Amendment 005 presentation-security rules  
**Applies to:** Original architecture handoff + Amendments 001–005  
**Intent:** Remove the overly restrictive prohibition on module-provided JavaScript/HTML while preserving the correct boundary between trusted code and untrusted data

---

# 1. Purpose

Amendment 005 correctly established that raw metadata should not become executable presentation data, but it was too restrictive in prohibiting arbitrary JavaScript/HTML from modules.

inventoryzing modules are **trusted installed extensions**.

A module may already execute trusted backend code and participate in privileged application behavior. It is therefore inappropriate to arbitrarily prohibit that same trusted module from providing rich frontend code.

This amendment replaces the relevant presentation restrictions in Amendment 005.

Where this amendment conflicts with Amendment 005, **this amendment takes precedence**.

---

# 2. Trust Model

Installing a module constitutes explicit trust in that module's code.

A trusted inventoryzing module MAY provide:

- backend code;
- frontend JavaScript or TypeScript;
- custom frontend components;
- custom pages and routes;
- custom CSS;
- module-specific interactive UI;
- declarative presentation providers;
- scanner-specific interfaces;
- custom dashboards;
- custom workflow interfaces;
- module-owned client logic.

The core MUST NOT pretend that such a module is sandboxed unless an actual sandbox is explicitly implemented.

---

# 3. Trusted Code vs. Stored Data

The important security boundary is:

> **Installed module code is trusted executable code. Persisted metadata and generic presentation data are not executable code by default.**

Therefore:

```text
module package:
    frontend.js
```

is trusted executable module code.

By contrast:

```text
metadata:
    some_string = "<script>...</script>"
```

is ordinary stored data and MUST NOT become executable merely because it contains HTML or JavaScript syntax.

---

# 4. Generic Rendering Must Remain Non-Executable

The core generic renderer MUST NOT automatically interpret arbitrary stored strings as:

- HTML;
- JavaScript;
- CSS;
- executable templates;
- event-handler source;
- arbitrary browser code.

For example, a metadata value containing:

```html
<script>alert("hello")</script>
```

MUST be treated as text by generic rendering paths unless trusted module code explicitly chooses to interpret it otherwise.

This prevents accidental self-XSS and data-to-code confusion.

---

# 5. Trusted Modules May Render Arbitrary UI

A trusted frontend module MAY intentionally create arbitrary DOM/UI using its own installed code.

For example, a manufacturing module MAY ship:

```text
ManufacturingTimeline.tsx
```

or equivalent client code that:

- loads manufacturing metadata;
- renders custom HTML;
- draws graphs;
- provides drag/drop interaction;
- performs client-side filtering;
- opens custom dialogs;
- invokes inventoryzing APIs.

This is permitted.

The module is trusted code.

---

# 6. Arbitrary HTML Is Not Independently Forbidden

Because a trusted frontend module may execute arbitrary JavaScript, separately prohibiting HTML generated by that code provides no meaningful security boundary.

Trusted module code MAY generate or render arbitrary HTML as part of its frontend behavior.

However, the core MUST distinguish:

```text
trusted module-generated UI
```

from:

```text
untrusted/raw stored strings
```

The latter remain non-executable by default.

---

# 7. Metadata Must Remain Presentation-Agnostic

Metadata remains machine-facing state.

Example:

```text
manufacturing.printer = <entity UUID>
manufacturing.material_used = 83.4 g
manufacturing.design_file = <blob UUID>
```

The metadata subsystem MUST NOT require persisted fields such as:

```text
display_html
display_javascript
display_template
```

for ordinary presentation.

The owning module decides how to render its metadata.

---

# 8. Declarative Presentation Remains Supported

The standard declarative presentation-component system remains valuable and SHOULD remain part of inventoryzing.

Example standard components include:

```text
Text
KeyValue
EntityLink
Quantity
Date
DateTime
Badge
FileDownload
Image
Table
List
ActionButton
Warning
Status
```

These components provide:

- consistent UI;
- portable rendering;
- easier Android/handheld support;
- compatibility with third-party clients;
- simpler module development.

However:

> **Declarative components are the portable/easy presentation path, not the maximum power available to trusted modules.**

---

# 9. Custom Presentation Is an Additional Capability

A module MAY provide both:

```text
portable declarative presentation
```

and:

```text
custom client-specific presentation
```

For example, a manufacturing module MAY expose a declarative summary:

```text
Printer: Prusa MK4 #2
Material used: 83.4 g
Design file: motor_mount.gcode
```

that any inventoryzing client can render.

The web UI MAY additionally load a rich custom module component providing:

- interactive print history;
- graphs;
- slicer previews;
- custom controls.

Clients that do not support that module's custom frontend MAY fall back to the declarative representation where available.

---

# 10. Cross-Client Compatibility Is Not Automatic

A custom web frontend module is not automatically portable to:

- Android handheld clients;
- terminal UIs;
- third-party frontends;
- future native applications.

If a module requires cross-client presentation, it SHOULD provide one or more of:

- declarative presentation;
- client-specific implementations;
- API resources that unsupported clients can display generically.

This is a compatibility concern, not a security restriction.

---

# 11. Module Manifest Capability Declaration

Modules SHOULD declare the extension capabilities they provide.

Example:

```yaml
module:
  id: manufacturing
  version: 1.2.0

capabilities:
  backend_code: true
  frontend_code: true
  custom_routes: true
  metadata_schemas: true
  presentation_providers: true
```

This declaration is primarily for:

- administrator transparency;
- compatibility checking;
- client capability negotiation;
- deployment tooling.

It does not imply sandboxing unless a future sandboxed module class is explicitly introduced.

---

# 12. Installation Trust Warning

If a module contains executable backend or frontend code, the installation UI SHOULD make that clear.

Example:

> This module contains trusted inventoryzing server and/or browser code. Installing it grants the module execution within the inventoryzing application environment.

The platform SHOULD NOT imply that arbitrary third-party modules are safe merely because they are packaged as inventoryzing modules.

---

# 13. Backend Authorization Remains Mandatory

Frontend trust does not replace backend authorization.

A module MAY render any UI it wants, but backend operations MUST still perform normal authorization.

For example:

```text
[Delete Asset]
```

may appear in a custom module UI.

The API handling the deletion MUST independently verify:

```text
current user has required permission
```

The system MUST NOT treat UI visibility as an authorization control.

---

# 14. Custom Frontend Code May Call APIs

Trusted frontend modules MAY directly call inventoryzing APIs, subject to the authenticated user's effective permissions and any module-specific service credentials explicitly granted.

They are not limited to declarative `ActionButton` components.

Therefore, Amendment 005's rule that declarative action buttons reference registered semantic actions remains valid **for that declarative component type**, but MUST NOT be interpreted as a prohibition on custom module client logic.

---

# 15. Declarative ActionButton Semantics

The standard declarative `ActionButton` component SHOULD continue to reference a registered semantic action/workflow.

Example:

```text
action_id = openlab.request_return
```

This makes portable declarative UIs predictable.

However, trusted custom frontend code MAY implement richer client-side interaction and call authorized APIs directly.

---

# 16. Stored Data Must Not Accidentally Become Code

The following MUST remain true even when arbitrary trusted frontend modules are supported:

1. raw metadata strings are not executed automatically;
2. blob contents are not injected into the DOM as executable markup by generic renderers;
3. presentation text is escaped by generic clients;
4. generic API responses are data;
5. custom code execution originates from installed trusted module assets or another explicitly trusted extension mechanism.

This is the primary XSS boundary.

---

# 17. Modules May Intentionally Interpret Their Own Data

A trusted module MAY deliberately define metadata that contains:

```text
HTML fragments
template source
script-like expressions
```

and MAY deliberately interpret that data.

If it does so, responsibility belongs to that trusted module.

The core does not need to prohibit this.

However:

- the core MUST NOT execute such content automatically;
- unrelated modules MUST NOT assume such data is safe executable content;
- the module SHOULD clearly own the namespace containing such data.

---

# 18. Same-Origin Implications

If trusted module frontend code executes in the primary inventoryzing web origin, administrators MUST understand that such code may have access to browser capabilities available to inventoryzing itself, subject to browser security mechanisms and application APIs.

This may include the ability to:

- inspect page state;
- make authenticated same-origin API requests;
- alter UI;
- register event handlers;
- interact with other same-origin module code.

This is accepted under the trusted-module model.

---

# 19. Future Partially Trusted Modules Are Separate

A future plugin ecosystem MAY introduce more restricted module classes such as:

```text
declarative-only modules
sandboxed iframe modules
isolated frontend bundles
capability-restricted plugins
```

Such a system would require an explicit sandbox and permission model.

It is outside the MVP.

The current architecture MUST NOT claim such isolation where none exists.

---

# 20. Server-Side and Browser-Side Trust Are Distinct but Both Explicit

A module MAY declare:

```text
backend_code: true
frontend_code: false
```

or:

```text
backend_code: false
frontend_code: true
```

or both.

Deployment tooling MAY allow administrators to inspect these capabilities before installation.

The architecture does not require all modules to have both forms of code.

---

# 21. Module Removal

Removing a module MAY remove:

- its backend handlers;
- its frontend assets;
- its custom routes;
- its custom presentation.

Persisted metadata remains subject to Amendment 004's preservation rules.

Therefore:

```text
module removed
    -> custom UI disappears
    -> module metadata remains preserved
```

unless an explicit destructive migration is performed.

---

# 22. Content Security Policy

inventoryzing MAY use browser Content Security Policy or similar browser protections.

Such policies SHOULD be designed to support installed trusted module bundles without requiring unsafe accidental string execution.

The platform SHOULD prefer loading registered module assets over broad mechanisms such as:

```text
eval()
```

or automatically executable inline strings.

This is an implementation hardening recommendation, not a restriction on module UI capability.

---

# 23. Recommended Module Presentation Model

The preferred hierarchy is:

```text
Module
├── metadata schemas
├── backend logic
├── semantic actions/workflows
├── declarative presentation
└── optional custom frontend code
```

A simple module may need only declarative presentation.

A complex module may provide a complete custom interface.

Both are valid.

---

# 24. Example: Manufacturing Module

Persisted state:

```text
manufacturing.printer = <Prusa MK4 #2 UUID>
manufacturing.material = <PETG spool UUID>
manufacturing.material_used = 83.4 g
manufacturing.design_file = <blob UUID>
manufacturing.completed_at = <timestamp>
```

Portable declarative presentation:

```text
Manufacturing

Printer: Prusa MK4 #2
Filament: PETG Black #4
Material used: 83.4 g
Design file: motor_mount_rev7.gcode [Download]
Time of manufacture: 08 Nov 2032
```

Optional custom web presentation MAY additionally provide:

```text
interactive job timeline
G-code preview
material-consumption graph
printer-history navigation
reprint controls
```

The core does not need to understand any of those manufacturing-specific interactions.

---

# 25. Example: OpenLab Module

The OpenLab module MAY provide:

```text
custom checkout kiosk page
custom scanner session UI
return queue dashboard
monitor controls
frontend timers
large touch/scanner-oriented interface
```

It is not required to construct such a workflow solely from generic declarative components.

Backend checkout/return actions remain subject to normal inventoryzing authorization and semantic invariants.

---

# 26. Revised Security Rule

The security rule from Amendment 005 is replaced with:

> **Trusted installed modules MAY execute arbitrary backend and frontend code and MAY provide arbitrary custom UI. Raw metadata and generic presentation data MUST remain non-executable by default. Backend authorization MUST remain authoritative regardless of frontend behavior.**

This is the normative boundary.

---

# 27. Acceptance Tests

The module/presentation subsystem SHOULD test at least:

1. installed trusted frontend modules can register and execute custom client code;
2. modules can register custom routes/pages/components;
3. modules can still use portable declarative presentation;
4. raw metadata containing HTML is displayed as non-executable text by generic rendering;
5. raw metadata containing JavaScript is not automatically executed;
6. a trusted custom module can intentionally render arbitrary UI;
7. backend permissions remain enforced even when custom UI attempts unauthorized API calls;
8. declarative `ActionButton` continues to resolve registered semantic actions;
9. custom frontend code is not artificially restricted to `ActionButton`;
10. uninstalling a module removes its custom frontend while preserving its metadata;
11. clients lacking custom-module support can use declarative fallback where provided;
12. module installation clearly indicates when executable frontend/backend code is present.

---

# 28. Final Clarification

inventoryzing does **not** use the model:

```text
modules are untrusted
therefore modules may only emit safe predefined widgets
```

Instead, it uses:

```text
installed module code = trusted extension code

stored metadata = data

generic presentation payload = data

backend authorization = authoritative permission boundary
```

The platform MUST avoid accidental data-to-code execution.

It MUST NOT arbitrarily cripple trusted extension code.

If a future deployment requires partially trusted plugins, that will be designed as a separate sandboxed extension class rather than retrofitted by pretending today's trusted modules are sandboxed.
